# دليل مراجعة Mawj قبل التسليم

**تنبيه لهذه النسخة:** هذا الفرع يستخدم قوالب Django وCSS وJavaScript بسيرفر واحد. شرح Next.js أدناه يخص النسخة الأصلية على `main`. راجع [شرح نسخة Django](django-edition.md) وREADME لهذا الفرع لتشغيل النسخة الحالية. النماذج وقواعد البيانات ومنطق الاقتراحات والتقارير مشتركة بين النسختين.

مراجعة بتاريخ 13 أكتوبر 2026 مقابل ملف **Capstone Project Guide** ذي الست صفحات. هذه مطابقة للأدلة الموجودة، وليست منحًا للدرجات. النسخة البرمجية التي بدأت بها المراجعة: `4c2500b`. جرى استنساخها من GitHub في مجلد جديد، وتثبيت حزم Python وNode، وإنشاء قاعدة جديدة وتعبئتها ببيانات وهمية، وبناء Next.js وتشغيل الواجهة والخادم والتحقق من التقارير عبر API. هذه تجربة Linux جديدة؛ ليست إثباتًا لتجربة جهازك أو وصول المدرّب.

## كيف تعمل النسخة الحالية؟

هناك واجهتان تستخدمان قاعدة البيانات نفسها:

- **Next.js**: الواجهة الجديدة، على المنفذ 3000 في التشغيل المحلي. تعرض الصفحات وتستدعي API.
- **Django**: مسؤول عن الحسابات والتحقق وقاعدة البيانات والذكاء والتقارير، على المنفذ 8000. يحتفظ أيضًا بقوالب HTML الأصلية؛ ليست هي التصميم الجديد.

مثال إنشاء مهمة:

`نموذج المهمة → frontend/lib/api.ts → تحويل /api/ في Next.js → config/api_urls.py → config/api.py → TaskForm → Task → SQLite → استجابة JSON → تحديث الواجهة`

أما المسار الأصلي في Django فهو:

`tasks/urls.py → tasks/views.py → forms/models وORM → templates/tasks/...`، مع وراثة التخطيط من `templates/base.html`.

JSON صيغة لتبادل البيانات؛ API طريق اتصال بين الواجهة والخادم. SQLite قاعدة بيانات علائقية في ملف `db.sqlite3`. إغلاق السيرفر لا يحذف هذا الملف. تنزيل المشروع في مجلد آخر قد ينشئ قاعدة جديدة، لذلك يجب الاحتفاظ بملف بياناتك وملفات الصور محليًا.

## خريطة الملفات

| الملف أو المجلد | دوره ولماذا أُضيف أو بقي |
|---|---|
| `manage.py` في الجذر | أوامر Django: التشغيل، الهجرات، الاختبارات، وبيانات العرض |
| `config/settings.py` | إعدادات Django: قاعدة البيانات، التطبيقات، التوقيت، التحميل من `.env`، واختيار المزوّد |
| `config/urls.py` و`config/api_urls.py` | تحديد الطريق الذي يقود إليه كل عنوان؛ الثاني خاص بالواجهة الجديدة |
| `config/api.py` | تنفيذ طلبات Next.js، مع جلسات Django وCSRF وتقييد السجلات بصاحبها |
| `config/asgi.py` و`config/wsgi.py` | نقاط تشغيل Django لخوادم الاستضافة؛ ليست صفحات للمستخدم |
| `accounts/` | التسجيل والدخول والملف الشخصي والصورة وتفضيلات الطابع؛ Django يحفظ كلمات المرور كقيم تجزئة (hash) للتحقق، لا كنص صريح |
| `tasks/models.py` | تعريف بيانات المهمة، مثل العنوان والتاريخ والحالة والتصنيف والتكرار |
| `tasks/forms.py` | التحقق على الخادم: العنوان، المدة، منع تغيير الموعد إلى الماضي، وغير ذلك |
| `tasks/services.py` | منطق مشترك مثل إكمال مهمة متكررة وإنشاء الموعد التالي دون تكراره |
| `tasks/views.py` و`tasks/urls.py` | صفحات المهام الأصلية ومساراتها في Django |
| `journal/` | بيانات اليومية والاقتراحات، النماذج، والمسار الأصلي لقبول الاقتراح أو رفضه |
| `dashboard/reports.py` | حساب الفترة والإجمالي والمكتمل والنسبة وبيانات الرسم، لتستخدمها الواجهتان |
| `dashboard/views.py` | صفحات التقويم والإحصائيات الأصلية |
| `ai/provider.py` | نقطة مشتركة لاختيار المزوّد، إرسال الطلبات، وقراءة النتائج والتحقق منها |
| `*/migrations/` | خطوات إنشاء وتحديث الجداول. يجب تسليمها وتشغيلها بـ`migrate`؛ ليست نسخًا من حسابات المستخدمين |
| `*/admin.py` | تسجيل النماذج في لوحة إدارة Django |
| `tests.py` و`test_*.py` | اختبارات القواعد والحسابات والملكية والواجهات البرمجية؛ تستخدم قاعدة اختبار منفصلة |
| `templates/` | قوالب Django الأصلية؛ مفيدة لشرح الوراثة ومسار URL → view → ORM → template |
| `frontend/app/page.tsx` | الصفحة التعريفية الرئيسية؛ أمثلتها التوضيحية ليست بيانات حسابك |
| `frontend/app/layout.tsx` | التخطيط العام، الخطوط، الطابع، واللغة الأولية من ملف ارتباط |

| `frontend/components/` | وحدات واجهة قابلة لإعادة الاستخدام: النماذج، المهام، اليوميات، التقويم، التقارير، الدخول والملف الشخصي |
| `frontend/components/dialog.tsx` | نافذة تفاصيل اليوم وتأكيد الحذف؛ تظهر داخل مجال الرؤية وتدعم الإلغاء |
| `frontend/components/theme.tsx` و`language.tsx` | اختيار الطابع واللغة وحفظهما |
| `frontend/lib/api.ts` | إرسال طلبات الواجهة، رمز CSRF، أخطاء الطلبات وتنسيق التواريخ |
| `frontend/lib/translations.json` و`i18n.ts` | النصوص العربية واختيار ترجمتها؛ لا تترجمان يوميات المستخدم أو مهامه |
| `frontend/app/globals.css` | ألوان الطوابع، تنسيق الصفحات والجوال واتجاه العربية |
| `frontend/app/fonts/` | ملفات Saudi المحلية للعناوين العربية |
| `frontend/next.config.ts` | إعداد Next.js، وتحويل طلبات `/api/` إلى Django |
| `frontend/package.json` و`package-lock.json` | حزم الواجهة وأوامرها؛ ملف القفل يثبت شجرة نسخ الحزم المستخدمة مع `npm ci` |
| `frontend/tsconfig.json` | إعداد فحص TypeScript، وهو JavaScript مع تعريفات أنواع تساعد على كشف أخطاء البيانات |
| `frontend/next-env.d.ts` | تعريفات يولّدها Next.js؛ لا تحتاج تعديلها يدويًا |
| `scripts/dev.mjs` | تشغيل Django وNext.js معًا من المجلد الصحيح، وإظهار المسار وفحص الجاهزية |
| `requirements.txt` | حزم Python المطلوبة، ومنها Django وRequests وPillow وpython-dotenv |
| `.env.example` | مثال آمن للإعداد. انسخه محليًا إلى `.env` إن احتجت إعداد مزوّد؛ لا تضع مفاتيح حقيقية في المثال |
| `.gitignore` | يمنع رفع قاعدة بياناتك وصورك ومفاتيحك والحزم والملفات المولّدة المعتادة |
| `docs/` | التصميم وERD، التشغيل، الاختبارات، وسيناريو العرض |
| `myproject/` | هيكل Django قديم غير مستخدم في التطبيق الحالي؛ التشغيل المعتمد من `manage.py` في الجذر. راجعه قبل التسليم لتنظيف الملفات دون حذف عشوائي |
| `.agents/` و`skills-lock.json` إذا وُجدا محليًا | أدوات مساعدة لعمل Codex ومهارات التصميم؛ ليست مطلوبة لتشغيل الموقع |

`node_modules/`، `.next/`، `.venv/`، و`__pycache__/` ملفات تثبيت أو بناء أو تخزين مؤقت. يعاد إنشاؤها، ولا تُسلّم بدلًا من المصدر. أما `db.sqlite3` و`media/` ففيهما البيانات والصور المحلية؛ احتفظ بهما عند تحديث نسختك، ولا ترفعهما ببيانات شخصية.

## الذكاء الاصطناعي وDemo بالتحديد

لم ندرّب نموذجًا جديدًا. جهّزنا اتصالًا اختياريًا بمزوّد خارجي، ووضعًا محليًا لتجربة المسار دون خدمة خارجية.

| الوضع | كيف يعمل؟ | هل يحتاج مفتاحًا أو يرسل النص للخارج؟ |
|---|---|---|
| `manual` | يحفظ اليومية كما كُتبت، دون اقتراحات | لا |
| `demo` | قواعد بسيطة تستخرج سطور القوائم أو عبارات نية معينة؛ تفاصيل المهمة تعود بأولوية `medium` ومدة **30 دقيقة ثابتة** | لا؛ ليس نموذج ذكاء اصطناعي |
| `gemini` / `openai` / `claude` | يرسل النص إلى الخدمة المختارة لاقتراح المهام أو تقدير الأولوية والمدة | نعم؛ مفتاح للمزوّد المختار وإتاحة نموذج مناسب |

مثال مضمون لوضع Demo:

```text
- مراجعة فصل قواعد البيانات
- إعداد شرائح العرض
```

ينتج اقتراحين من السطرين. لا يفهم جميع صيغ العربية، ولا يعيد تحرير النص مثل نموذج حقيقي. نجاح Demo يثبت مسار العرض والقبول والحفظ، ولا يثبت جودة النموذج الخارجي.

مسار اليومية:

1. يحفظ `JournalEntry.raw_text` النص الأصلي.
2. تستدعي طبقة Django `process_journal` في `ai/provider.py`.
3. في الوضع الحقيقي تُرسل تعليمات للمزوّد تطلب نصًا مرتبًا واقتراحات بصيغة JSON، دون اختراع مهام، وباللغة التي استخدمها صاحب اليومية.
4. يتحقق الكود من صيغة الرد والعنوان والأولوية والمدة والتاريخ. تُزال المواعيد المقترحة التي مضت.
5. يُحفظ النص الناتج في `clean_text` والاقتراحات في `TaskSuggestion` بحالة `pending`؛ لا تصبح مهام تلقائيًا.
6. قبول المستخدم للاقتراح ينشئ `Task` ويغيّر حالة الاقتراح إلى `accepted`. الرفض يغيّرها إلى `dismissed`.
7. عند فشل الخدمة أثناء إنشاء اليومية، يُحفظ النص كما كُتب مع تنبيه. فشل اقتراح تفاصيل المهمة لا يعني حفظ تعديل تلقائي.

حذف اليومية يحذف اقتراحاتها، بينما تبقى المهام المقبولة مستقلة. تعديل اليومية يحفظ النص المعدّل كما كُتب ويلغي الاقتراحات المعلّقة القديمة؛ التحليل من جديد إجراء مستقل.

**`seed_demo` شيء مختلف:** أمر يضيف حسابًا وهميًا و13 مهمة وتدوينتين وثلاثة اقتراحات للعرض. لا يشغّل نموذج AI. الحساب يحتاج كلمة مرور تختارها محليًا، وإعادة الأمر لا تستبدل الحساب الموجود. الوضع الافتراضي `AI_PROVIDER=demo` مستقل عن وجود هذه البيانات.

للذكاء الحقيقي: انسخ `.env.example` إلى `.env` وحدد مزوّدًا واحدًا ومفتاحه محليًا، ثم أعد تشغيل السيرفر. الإعداد من بيئة العملية يتقدم على الملف. لا ترسل المفتاح في المحادثة أو ترفعه إلى Git. لم تُختبر خدمة حقيقية في هذه المراجعة؛ اختبارات المزوّد تستخدم ردودًا محاكية.

## ما يجب أن تقدري على شرحه في المناقشة

- لماذا اخترت Django للخادم وNext.js للواجهة، وما الفرق بين API والقوالب الأصلية؟
- لماذا ترتبط كل مهمة وتدوينة بمستخدم، وكيف يمنع الخادم الوصول لسجلات الآخرين؟
- لماذا نفصل الاقتراح عن المهمة، وما الذي يحدث عند القبول والحذف؟
- أين يعمل التحقق على الخادم، ولماذا لا يكفي منع الخطأ في المتصفح؟
- الفرق بين التجميع وAnnotation: إجمالي المهام مقابل عدد الاقتراحات المعلّقة لكل تدوينة.
- النسبة: `المكتمل ÷ إجمالي مهام الفترة × 100`، بعد التقريب. مثال: 6 من 12 = 50%. الفترة تعتمد تاريخ جدولة المهمة، أو تاريخ إنشائها إذا لم تكن مؤرخة؛ ليست سجل أحداث الإنجاز.
- الفرق بين الذكاء الحقيقي وDemo وبيانات العرض، وحدود كل منها.

## اختبار قبول يدوي على جهازك

سجّلي النتيجة الفعلية في جدول القبول داخل `verification.md`:

1. إنشاء حساب وهمي، ثم الخروج والدخول. إغلاق السيرفر وإعادة تشغيله، ثم الدخول للحساب نفسه.
2. اختيار اللغة والطابع في الدخول، والتأكد من بقائهما بعد الدخول وتحديث الصفحة.
3. إنشاء يومية بالنقطتين أعلاه، قبول اقتراح، ثم العثور عليه ضمن المهام وإكماله.
4. تجربة حقل مطلوب فارغ وموعد مضى؛ التأكد من رفضهما مع رسالة واضحة.
5. البحث والتصفية بنتائج مطابقة وبلا نتائج، وتعديل مهمة وحذفها من نافذة التأكيد.
6. الضغط على يوم في التقويم والتأكد من ظهور مهامه ونص يومياته كاملًا.
7. مقارنة الإحصائيات ببيانات ذات أعداد معروفة، وإظهار عدد الاقتراحات المعلّقة لكل تدوينة.
8. حذف يومية ذات اقتراح مقبول والتأكد من بقاء المهمة، وتجربة مستخدم آخر للتأكد من الخصوصية.
9. تكرار المسار على هاتف، والتنقّل بين الحقول والأزرار بلوحة المفاتيح.
10. التأكد من وصول المدرّب للمستودع، وأن نسخة العرض هي نسخة التسليم نفسها.

النشر ليس شرطًا عامًا. إن لم تختبري مزوّدًا حقيقيًا، قدّمي Demo بوضوح بوصفه محاكاة، ولا تصفيه بأنه نموذج يعمل فعليًا. ملاحظات المستخدمين والنطاق المعتمد والفهم الفردي أدلة يجب أن تقدّميها بنفسك.
